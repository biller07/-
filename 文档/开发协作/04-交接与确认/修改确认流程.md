# 修改确认流程

## 为什么需要两次提交

第一次提交固定已核对的实现内容，产生可查看、可回退的实现哈希。第二次提交只保存修改确认、任务状态和交接信息。这样项目所有者在确认前就能精确审查实现，不会出现“确认文件引用尚不存在的提交”。

## 标准流程

1. 开发者把任务改为“待核对”，完成 `提交前核对清单.md`。
2. 核对通过后，只暂存本任务路径并创建实现提交。
3. 取得实现提交完整哈希，在 `协作记录/修改确认/确认记录/` 新增确认文件。
4. 把任务板和进度总表改为“待确认”，创建确认提交并推送功能分支。
5. 项目所有者查看确认文件、核对报告和实现提交：
   - 同意：填写确认信息，任务改为“已确认”，再合并 `main`；
   - 要求修改：任务退回“开发中”，创建新提交并重新核对；
   - 暂缓：保持“待确认”，不得合并。
6. 合并后登记合并提交，任务才改为“已完成”。

## 回退原则

优先使用 `git revert <实现提交>` 创建可审计的反向提交。不得在共享分支使用强制推送或硬重置抹除历史。涉及数据库迁移时，必须先执行迁移文档定义的回退或补偿步骤。
